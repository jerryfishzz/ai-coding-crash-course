Authorize the resource, not just the role

“Is this person an instructor?” is not enough. For a course mutation, the server must also ask whether this instructor is allowed to edit this particular course.

Two layers of authorization in the course editor

In instructor.$courseId.tsx, both the loader and action check that the user is an instructor or admin. The action then looks up the route’s course ID and checks ownership:

role allowed?
AND
(course.instructorId === currentUserId OR user.role === Admin)

An instructor can edit their own course. An admin can edit any course. Another instructor gets 403 even if they manually change /instructor/12 to /instructor/13. Checking only the broad role would leave an object-level authorization gap, commonly called IDOR (insecure direct object reference). OWASP recommends checking permission for the specific object on every access attempt: IDOR prevention guidance.

Nested IDs need their own relationship check

The action also accepts IDs for modules and lessons. Before renaming or deleting a module, it loads that module and verifies mod.courseId === courseId. Otherwise a user might submit the ID of a module from a different course. The parent course check and child-to-parent check protect different relationships.

The action checks the user role, parses the course route parameter, loads the course, and checks ownership before reading/validating the form and calling a write service. Every route that exposes or mutates a resource needs the appropriate object-level check; a check in one page does not protect another action.

Authorization is about subject + action + resource. “Instructor” says who the caller is; ownership says whether they may edit this course; the module/course check says whether this child ID belongs in this operation.

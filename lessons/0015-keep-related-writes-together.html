Keep related writes together

When one user operation needs multiple database writes, decide whether they must succeed or fail as one unit.

Follow the self-purchase branch

In courses.$slug.purchase.tsx, a valid self-purchase calls createPurchase(...) and then enrollUser(...). Those services each execute their own insert through the shared database connection.

purchase confirmation → insert purchase row → insert enrollment row → welcome redirect

These records describe one expected outcome: the user has paid for and gained access to a course. But in the current code, the two inserts are not visibly grouped in a transaction. If the purchase insert succeeds and the enrollment insert then fails, the first row can remain without the second. That is a partial success the application may not want.

Transaction = one commit decision

A database transaction groups statements into a logical unit. If its callback finishes successfully, the writes commit; if an error escapes, they roll back together. Drizzle documents this API for SQLite as well as other drivers; see the transaction guide.

BEGIN → insert purchase → insert enrollment → COMMIT
                  ↘ error → ROLLBACK both

For this repository’s better-sqlite3 setup, transaction callbacks are synchronous. A possible design is to let the service functions accept a transaction handle (or move both inserts into one higher-level service) and run both queries with that same handle. This is a design sketch, not a change made here.

Use a transaction when partial completion would violate the operation’s meaning. It gives database atomicity; it does not automatically cover emails, HTTP calls, or other external side effects.

Testing the invariant

A useful failure-path test arranges for the second step to fail after the first insert has run. Then assert the operation fails and that neither row remains. The important claim is not just “an error happened”; it is “the purchase and enrollment stay consistent.” A success-path test should also assert that both rows exist.

Quick recall

If purchase creation succeeds but enrollment creation fails, what does a transaction protect?

Practice

Trace the self-purchase path in the route. If createPurchase succeeds and enrollUser throws, what database state could be left behind today? Then describe one failure-path test that would prove a transaction keeps the two records consistent. Bonus: why should welcome-email delivery (if added later) not be assumed to roll back with this database transaction?

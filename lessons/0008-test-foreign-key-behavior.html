Test foreign-key behavior safely

A database rule is worth testing against a real SQLite engine. This repo already has an isolated, in-memory test database that uses the same migrations as the app.

Find the safety boundary

createTestDb opens SQLite with :memory:, enables PRAGMA foreign_keys = ON, and applies the project’s drizzle/ migrations. Service tests replace the normal database import with this fresh test database. They don’t delete rows from your working data.db.

For module deletion, the current schema says lessons.moduleId references modules.id, while progress rows also reference lessons. The existing moduleService.test.ts tests deleting a module with lessons but no history. A useful complementary case adds lesson progress first.

Arrange → act → assert

Arrange: module + lesson + progress row
Act: call deleteModule(module.id)
Assert: FK error; module and lesson still exist
// Sketch in moduleService.test.ts; use its existing testDb/base helpers
const mod = createModule(base.course.id, "History", 1);
const lesson = createLesson(mod.id, "Lesson 1", null, null, 1, null);
testDb.insert(schema.lessonProgress).values({
  userId: base.user.id,
  lessonId: lesson.id,
  status: schema.LessonProgressStatus.InProgress,
}).run();

expect(() => deleteModule(mod.id)).toThrow();
expect(getModuleById(mod.id)).toBeDefined();
expect(testDb.select().from(schema.lessons).all())
  .toContainEqual(expect.objectContaining({ id: lesson.id }));

This test documents what the current policy does: learner progress blocks deleting that lesson, so the service throws and does not reach the module delete. Another test could assert the error message after the route/service is improved. Keep each test focused on one behavior. See Vitest’s official guide to structuring tests.

Use the same migrations and enable the same constraints. Otherwise, a test database can quietly behave differently from the real app. A fresh in-memory database makes it safe to try both the blocked-delete policy and a future archive/cascade policy.

Deletion policy and transactions

The module-delete bug is more than a missing cleanup query. It raises two design questions: which related data should survive, and how can a multi-step delete avoid leaving a half-finished result?

The relationship tree

course → modules → lessons
lessons → progress, quizzes, video events
quizzes → questions, attempts
questions → options, answers
attempts → answers

When a module is deleted, the immediate child rows are lessons. Those lessons can themselves have saved progress, quizzes, and video events. Quiz records have further dependent rows. A cascade on just lessons.moduleId would delete lessons, but the lesson-level references would still block that operation unless those relationships also had a deliberate delete policy.

Choose behavior from product meaning

  • Restrict: refuse deletion while dependent data exists; explain the reason or archive the content instead. The repo currently uses NO ACTION foreign keys.
  • Cascade: deleting a parent automatically deletes configured children. This is concise, but can erase learning history. Every edge in the relationship tree needs an intentional policy.
  • Explicit cleanup: delete dependent rows in a known order, then the parent. Put the steps in a transaction so all changes commit together or roll back together.

SQLite describes ON DELETE CASCADE as propagating a parent deletion to child rows. The behavior is declared per foreign key; see the official foreign-key actions guide. Drizzle’s transaction API groups related statements into one commit/rollback unit.

Decide what the product promises first. If quiz attempts and progress are valuable history, deleting course content may need to be blocked or archived. If they should disappear with their lesson, define that cascade intentionally. Then make the whole operation atomic.

Quick recall

What should decide whether deleting content also deletes learning history?

Apply it to this repo

In deleteModule, the service issues two separate deletes and has no transaction. In the current data, deleting lessons is blocked by progress, quiz, and video-event rows. If the product chose explicit cleanup, each dependent record would need a policy and cleanup step; a transaction would ensure a failure does not leave only some tables changed. No migration should be added until the intended retention behavior is clear.

Ask me about any part of that decision. For a next practice, pick one: preserve history by archiving modules, restrict deletion when history exists, or cascade-delete it. Explain the tradeoff before suggesting code.

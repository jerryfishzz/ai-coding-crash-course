Repo field guide

Plan a related-data delete

  1. Map parent → child relationships all the way down.
  2. Ask what must survive: history, audit data, user progress, or nothing.
  3. Choose restrict, archive, cascade, or explicit cleanup for each relationship.
  4. For explicit multi-table cleanup, use a transaction so it commits or rolls back as one unit.
  5. Match service behavior and foreign-key actions to that policy.
Restrict → preserve child rows; block parent delete
Cascade → delete configured child rows
Explicit cleanup → application orders deletes
Transaction → all changes commit or all roll back

Concrete module examples

Archive the module: add archivedAt (or an archived boolean) to modules, then set it on the module row. Its lessons, progress, quizzes, and video events remain unchanged. Normal course/module listings filter out archived modules; a history/admin view can still include them. Because this is one row update, it is already atomic. If the operation also updates child rows, group those updates in a transaction.

Restrict deletion: before deleting, check whether the module has lessons with progress, quiz attempts, or watch events. If it does, return a clear message such as “This module has learner history; archive it instead.” Keep the foreign keys as the final guard. Example: a lesson with a quiz attempt should stop deletion rather than silently erase that result.

Cascade deletion: with ON DELETE CASCADE on each edge, deleting a module can flow through modules → lessons → progress / quizzes / video events and quizzes → questions / attempts → answers. Every edge along a dependent path must allow the cascade; one remaining NO ACTION edge can block the statement. SQLite applies the cascades as part of the parent delete statement. This is a deletion policy, not just a convenience.

Why not cascade everything by default? If every foreign key in the database cascaded, deleting a course could also erase enrollments and purchases; deleting a user could erase learning progress and quiz history. Those may be records the product must retain. Choose the policy relationship-by-relationship, based on what the data means.

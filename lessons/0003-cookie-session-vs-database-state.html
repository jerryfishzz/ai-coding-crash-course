Cookie session or database row?

Your route trace was solid. The next distinction is about where a value belongs: a per-browser choice often belongs in session state; lasting facts about the product belong in domain tables.

Trace what this app does

DevUI form → POST /api/switch-user → action validates userId → setCurrentUserId changes session → redirect responds with Set-Cookie

You correctly found the form, route, and validation. One refinement: the session value is set inside setCurrentUserId, where session.set("userId", userId) updates the in-memory session object and commitSession creates the cookie value. The action then attaches that cookie to the redirect response with Set-Cookie. React Router’s createCookieSessionStorage stores session data in the cookie itself, so this path does not update SQLite. That is why you do not see a sessions table in this database.

Model by lifetime and meaning: “which user am I simulating in this browser?” is session context. “who is this user?” is durable account data in the users table.

When would a service and migration belong?

When a feature creates a durable domain fact, model that fact in the table that owns it. For example, enrolling a user in a course belongs to enrollment data and its service—not automatically to userService or a new column on users. A column such as current_user would put browser/session selection on the user’s shared account row, where it could conflict across sessions.

Your instinct to look for an existing persistence pattern was sound. If this app instead stored session data on the server, a separate session store or table could be appropriate. In this repo, the storage choice is already cookie-backed; adding a current_user column would change the meaning and sharing scope of the value instead of following the session pattern.

For a real schema change in this repo, update app/db/schema.ts, run npm run db:generate, inspect the generated SQL in drizzle/, then run npm run db:migrate. Drizzle’s guides explain migration workflows; React Router’s session guide describes cookie-backed and database-backed alternatives.

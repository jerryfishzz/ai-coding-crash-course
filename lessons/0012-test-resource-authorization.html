Test resource authorization

A useful access-control test uses two users and two resources. It proves both that the right owner can act and that changing an ID cannot cross the ownership boundary.

Arrange two separate ownership branches

Instructor A → Course A → Module A
Instructor B → Course B → Module B

The course editor action checks the caller’s role and course ownership. For module operations, it also checks that the module belongs to the course in the route. These checks lead to two different denial cases.

Two requests, two guards

  1. Wrong course: Instructor A posts to /instructor/Course-B. The course exists, but belongs to B, so the action returns 403 before mutation.
  2. Wrong module: Instructor A posts to their own /instructor/Course-A, but changes the submitted moduleId to Module B. Course ownership passes; the module/course relationship check rejects it with 404. Module B remains unchanged.
  3. Allowed case: Instructor A edits Module A. Verify the expected write succeeds.

Test the denied outcome and persisted state. A 403/404 alone is not enough if a bug performed the write before returning. OWASP recommends testing with multiple accounts and attempting to substitute another user’s object identifier: IDOR prevention guidance.

Fit it to this repo

createTestDb already provides isolated SQLite with real migrations, and app/services/*.test.ts replaces the app DB import with that test database. The repo currently has service tests but no direct course-editor action test. A route test would additionally need to send an authenticated session cookie (the route reads identity from the session) and submit valid form data, so it exercises the actual action guards.

Test permissions as a matrix: allowed role + owned resource succeeds; allowed role + someone else’s resource is denied; correct course + wrong child ID is denied; denied attempts leave stored data unchanged.

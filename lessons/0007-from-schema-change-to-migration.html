From schema change to migration

A TypeScript schema describes what the app expects. A migration is the versioned set of database instructions that brings a real SQLite file to that shape.

Four steps, four different jobs

schema.ts → npm run db:generate → review a new SQL file in drizzle/ → npm run db:migrate → SQLite database
  1. Declare intent: change the Drizzle schema, for example adding nullable archived_at to modules.
  2. Generate: Drizzle Kit compares the TypeScript schema with its migration snapshots and writes SQL. This does not itself update the database.
  3. Review: read the SQL as a code change. Check what tables/constraints change and whether existing rows are preserved.
  4. Apply: npm run db:migrate runs unapplied migrations against the configured database. Afterward, update service queries and UI to use the new field.

These are the scripts in this repo’s package.json, and drizzle.config.ts points Drizzle Kit at app/db/schema.ts, the drizzle migration folder, and data.db. The checked-in migration files show the SQL that is actually applied. Official guides: Drizzle Kit generate and migrate.

Use the module decision as an example

If the product chooses archive, a schema addition such as archivedAt: text("archived_at") changes the database shape. Existing module rows need a sensible value (often NULL means “not archived”). Then service queries must exclude archived modules from ordinary views. Adding the column alone does not implement the full feature.

If the product instead chooses cascade, changing .references(() => modules.id) to include an onDelete policy changes foreign-key behavior. Review the generated SQL carefully: a foreign-key change can require rebuilding a SQLite table, and every edge in the cascade path needs the intended policy. Do not infer the effect from the TypeScript line alone.

Schema edit ≠ database update ≠ completed feature. Generate and inspect the migration, apply it deliberately, then update and verify the code paths that depend on the new behavior.

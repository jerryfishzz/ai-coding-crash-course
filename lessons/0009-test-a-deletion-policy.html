Turn deletion policy into tests

A test is a precise statement of product behavior. The same “delete module” request should have different assertions depending on whether history is restricted, archived, or cascaded.

Same starting data, different promises

Arrange a module with a lesson, a progress row, a quiz attempt, and a video-watch event. Those rows represent learner history in this repo. Perform the chosen operation, then check the rows that matter—not only whether the service returned without throwing.

Restrict → deletion refused; all history remains
Archive → module marked archived; history remains; normal listing hides it
Cascade → module and intended descendants are removed

Translate the promise to assertions

  • Restrict: expect the service/action to refuse deletion with a useful reason. Query afterward and prove the module, lesson, progress, quiz attempt, and event remain.
  • Archive: expect the archived marker to be set. Prove lesson/history rows remain. Also test the read behavior: ordinary course listings omit the module, while an admin/history query can still find it if that is the chosen design.
  • Cascade: expect successful deletion. Query afterward and prove the module and each intended dependent row are gone. Also prove unrelated data—such as another module’s lesson/history—remains.

This is a contract test: it captures what callers and learners should observe. Vitest recommends focusing tests on behavior; SQLite applies foreign-key actions along declared relationships. See Vitest testing in practice and SQLite foreign-key actions.

Test both what changes and what must not change. “Delete succeeded” alone cannot tell you whether important history disappeared—or whether unrelated records were accidentally removed.

Quick recall

For a cascade-delete policy, what should a test check besides successful completion?

Practice

Pick one policy—not because we have chosen it for the product, but to practise. For a module with one lesson, progress, quiz attempt, and watch event, state: (1) what happens to each row, and (2) one nearby row that should remain unchanged. Then turn those statements into assertions.

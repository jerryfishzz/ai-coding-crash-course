Application rules and foreign keys

Category deletion shows two layers protecting the same relationship: the service explains the business rule; the database preserves referential integrity even if a caller bypasses that service path.

Follow the delete request

Delete button → deleteFetcher.submit → authorized route action → deleteCategory counts courses → if none, Drizzle deletes category → SQLite foreign key protects references

The route action checks that the current user is an admin, validates the delete intent and category ID, then calls deleteCategory. If the service throws, the action returns an error message; the UI displays it. That gives the user a useful explanation such as “2 courses use this category.”

The service checks courses.categoryId for references before deleting. This is an application-level rule: it can explain why deletion is refused. The schema also declares courses.categoryId as a foreign key referencing categories.id. Its migration uses ON DELETE no action, so SQLite rejects a delete that would leave courses pointing at a missing category. This project enables SQLite foreign-key enforcement with PRAGMA foreign_keys = ON when opening the connection.

Two layers, different jobs: the service guard gives a friendly domain error; the foreign key is the final integrity rule. SQLite documents that a parent row cannot be deleted while dependent child rows remain when foreign keys are enabled. See SQLite’s foreign-key guide.

Quick recall

If code bypassed deleteCategory, what still prevents orphaned courses?

Small architecture lesson

Use application checks for domain-specific messages and early feedback. Keep database constraints because other code paths, scripts, or future changes may bypass the service. Here the category and course relationship already exists, so deletion needs no migration; a new constraint or changed delete policy would.
